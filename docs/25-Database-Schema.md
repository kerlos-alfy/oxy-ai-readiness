> **Canonical note (ADR-004):** `oxy_settings`'s `key`/`value` columns are renamed to `setting_key`/`setting_value` (`KEY` is a MySQL/MariaDB reserved word). A formal naming-convention section has been added below. See `.project/adr/ADR-004-database-naming.md`.

---

# Purpose

The Database Layer stores all operational, historical and analytical data generated by Oxy AI Readiness.

The schema is designed for scalability, auditability and future cloud synchronization.

The plugin should minimize writes to the WordPress options table and instead use dedicated tables for operational data.

---

# Vision

Configuration belongs in WordPress.

Operational data belongs in dedicated tables.

Historical data should never be lost.

############################################################

NAMING CONVENTIONS (ADR-004)

############################################################

Table prefix

{$wpdb->prefix}oxy_{domain}, snake_case, plural for collection tables

Primary key

id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT on every table

Foreign keys

{referenced_table_singular}_id

Timestamps

created_at / updated_at, DATETIME, UTC

Reserved words

Never used as a bare column name (key, value, order, group, condition, read, check, range, desc, etc.). When the natural name is a reserved word, prefix it with the entity it belongs to (example: setting_key / setting_value on oxy_settings).

Cloud sync fields

uuid, version, checksum, updated_at, sync_status — optional, added only to tables explicitly flagged for cloud sync, not required on every table.

# Success Criteria

The database schema should support millions of audit records, years of historical data and future cloud synchronization without requiring structural redesign.

All schema changes must be migration-driven, reversible and backward compatible.
